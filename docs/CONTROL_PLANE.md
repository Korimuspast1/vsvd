# VSVD Control Plane и админка

Этот сервис — второй этап после рабочего Telegram-транспорта. Он существует для функций **VSVD**, а не как промежуточный сервер Telegram.

## Откуда берутся данные

| Данные | Источник | Где обрабатываются |
| --- | --- | --- |
| Чаты, сообщения, медиа, контакты, Telegram-авторизация | Telegram / транспорт встроенного Android-клиента | Только устройство пользователя |
| Темы, манифесты плагинов, публичные ключи, список отзыва | VSVD Control Plane | Сервер + локальный кэш клиента |
| Кастомные бейджи | Администратор VSVD | Сервер + кэш клиента |
| Роли админов и аудит | Администратор VSVD | Сервер |

Сервис не принимает Telegram-коды, 2FA-пароли, auth keys, сообщения или медиа.

## Предложенная архитектура

```text
Android VSVD ── HTTPS ──> API Control Plane ──> PostgreSQL
                               │
                               ├── S3-совместимое object storage (подписанные plugin-пакеты)
                               └── Admin web (отдельный origin)

Android VSVD ── Telegram client transport / MTProto ──> Telegram
```

Рекомендуемый стек: API на Kotlin/Ktor или TypeScript/Fastify, PostgreSQL, object storage, отдельное React/Next admin-приложение. Выберем одну реализацию в начале второго этапа; для текущего Android этапа сервер не запускается намеренно.

## Связывание Telegram-профиля и VSVD-бейджей

Нельзя доверять `telegramUserId`, который просто прислал клиент. Для выдачи бейджей нужен подтверждённый link:

1. Пользователь входит в VSVD локально через встроенный Telegram-транспорт клиента.
2. В приложении создаётся короткий одноразовый код привязки от Control Plane.
3. Пользователь отправляет этот код официальному боту VSVD (`/link код`).
4. Webhook бота получает Telegram `from.id`, сверяет код и создаёт связь с серверным профилем.
5. Клиент запрашивает только публичную карточку бейджей для подтверждённого ID и проверяет подпись ответа.

Бот обрабатывает только служебную команду привязки и не должен читать/сохранять личные чаты. Токен бота будет храниться только в секрете развернутого сервера.

## Минимальные таблицы

- `admin_users`, `admin_roles`, `admin_sessions`;
- `telegram_links` — внутренний ID, Telegram ID, время привязки, состояние;
- `badge_templates` — название, SVG/asset, цвет, правила;
- `badge_grants` — шаблон, получатель, выдал, срок, причина, статус;
- `plugin_publishers`, `plugin_versions`, `plugin_revocations`;
- `audit_log` — кто и когда выполнил административное действие, IP/UA с ограниченным хранением.

Telegram ID и информация о выдаче бейджа — персональные данные. Нужны доступ по ролям, минимальные сроки хранения, экспорт/удаление по запросу и журналирование доступа.

## Админка: первый набор действий

- вход администратора через passkey + TOTP или защищённый корпоративный SSO;
- создание шаблона бейджа с предпросмотром в VSVD;
- поиск только по уже привязанному пользователю;
- выдача, массовая выдача по явным спискам и отзыв бейджа;
- срок действия, причина и обязательная запись аудита;
- ключи издателей, публикация/отзыв плагинов;
- никакой возможности посмотреть Telegram-сообщения, сессии или коды авторизации.

## До публичного запуска

- HTTPS, HSTS, rate limit, CSRF-защита и строгая Content Security Policy;
- RBAC, минимум два независимых администратора для критических операций;
- хэширование session-токенов, шифрование резервных копий, ротация ключей;
- отдельные dev/staging/prod окружения;
- резервное копирование PostgreSQL и процедура отзыва скомпрометированного ключа плагина;
- политика конфиденциальности и проверка условий Telegram перед распространением APK.
